# 弱网场景与效果观测

## 使用与重复执行

入口：工具 → 手游弱网测试 → **场景配置与效果观测**。需要助手 **1.0.3**；旧助手请点击侧栏“更新 VPN 弱网助手”，并确认 VPN 授权。

1. 选择目标应用包名，载入四阶段模板：正常 10 秒 → 高延迟 15 秒 → 短时断网 5 秒 → 恢复 10 秒。
2. 修改各阶段名称、秒数、上下行带宽、延迟/抖动及 UDP 丢包/重复/乱序；可增删、排序，最多 20 个阶段，总时长 10～3600 秒。
3. 输入场景名称和 seed，点击“保存配置”。本机最多保存 50 个场景；同名覆盖和删除均需确认。修改名称可另存一份。
4. 点击“执行此配置”，在目标应用中产生流量。场景在同一 VPN/代理会话内切换，不会在阶段之间重启 VPN。
5. 观察阶段对照表、吞吐、连接数和 UDP 计数，结束后导出 JSON 报告。执行中的报告也可导出为当时的快照。
6. 重启桌面程序后，从“已保存场景”载入相同配置再执行；或将最近一次报告的配置载入编辑器。每次执行都有新的任务/运行 ID。

编辑器与运行配置隔离，编辑不会热改正在运行的任务。“执行此配置（替换当前任务）”会先停止旧任务。关闭对话框不停止测试，侧栏和任务中心均可停止。

seed 固定随机决策流；配置和输入处理顺序一致时可重现决策，但流量到达顺序、系统调度、服务器状态及应用超时不受 seed 控制，因此不是网络流量重放，也不保证每次丢掉同一批数据报。

## 时钟与恢复语义

- 只有桌面端确认 VPN 已启动，才启动场景的单调时钟。调度器每 100 ms 检查绝对经过时间，不累计每阶段等待的漂移。报告同时记录计划和实际阶段起止时间；系统挂起或调度延迟时可能有晚切换或未获得执行时间的阶段。
- 正常/恢复阶段可以所有参数为零：0 Kbps 为不限速，不额外加延迟或丢包，但仍经过 VPN、ADB 和桌面代理，不等于裸链路基线。
- 短时断网暂停 TCP 有效载荷转发和新建连接的转发，丢弃新到 UDP。TCP 字节不被删除，应用可能因超时主动断开；不会关闭设备 Wi-Fi/移动网络。
- 阶段变化取消旧的限速等待，按新配额执行。未写入的排队 UDP 作废并计数；已经部分写入的 UDP-over-TCP 帧在新阶段暂停/恢复，维持帧完整性。已进入 OS 缓冲的数据无法撤回。
- 场景正常结束由桌面端停止代理和助手。设备端兜底到期时长为场景总时长 **+90 秒**（最多 3690 秒），留给启动确认和紧急恢复。桌面崩溃时可能等待这段缓冲才恢复，不应把兜底时间当成场景有效测量时长。
- 报告记录正常完成、手动停止、任务取消、被新场景替换或设备端提前结束。设备 VPN/反向映射的清理结果在统一任务中心显示。

## 配置值与实际测量值

报告中的 `configured` 是启动时的完整场景快照；`measured` 是全程计数；`phases` 保留各阶段配置、计划/实际时间及独立计数；`samples` 为约 1 秒一次的实测采样（阶段边界和结束额外采样，记录实际窗口）。采样有数量上限 3700。

| 指标 | 口径与限制 |
| --- | --- |
| 上/下行 Kbps 配置 | 对该方向的所有 TCP/UDP 连接共享的有效载荷配额，不是单连接配额，不包含隧道头 |
| 实测有效载荷吞吐 | 成功 socket 写入的 TCP 字节 + UDP 字节，乘 8 / 实际毫秒；数值单位 Kbps（十进制） |
| 阶段/全程平均吞吐 | 包含空闲、断网及该阶段实际经过的时间，不是只在发送期间求平均 |
| TCP 活跃/峰值/累计 | 成功建立的代理出站 TCP 连接；失败单列 connectionErrors |
| UDP 活跃/峰值/累计 | SOCKS UDP-over-TCP 关联，不是 UDP 远端地址/会话数量 |
| UDP 队列当前/峰值 | 全会话、双方向共享，含排队和正在处理的数据报，上限 256；不包括内核或设备缓冲 |
| shapingWaitMs | 已完成配额申请的等待累计（含互斥等待），并发累计可大于墙钟时长；不包括取消的申请及附加延迟等待 |

测量点是桌面代理 socket 写入成功，不是对端应用确认收取。字节数包含成功发送的模拟重复包，不含 IP/TCP/SOCKS 帧头；既不是网卡线速，也不是应用去重后的唯一有效吞吐。局部写入后出错，只计已经成功写入的有效载荷。

### 丢弃原因分开记录

两个方向分别记录：

- `udpReceivedDatagrams`：代理收到的数据报。
- `udpPolicyEvaluated`：进入配置丢包随机判断的样本（断网包不进入）。
- `udpConfigDrops`：配置丢包策略命中。
- `udpQueueOverflowDrops`：未命中配置丢包，但共享队列已满。
- `udpOutageDrops`：短时断网阶段新数据报被丢弃。
- `udpPhaseChangeDrops`：阶段变化后尚未发送的处理任务/剩余副本作废。
- `udpCancelledDatagrams`：停止或连接关闭时取消的在途处理任务。
- `udpSendErrors`：解析目标、创建目标转发或发送失败的处理任务。
- `udpForwardedDatagrams`、`udpDuplicateDatagrams`：成功发送总数，以及其中的重复副本数量。

**实测配置丢包比例 = udpConfigDrops / udpPolicyEvaluated。** 没有策略样本显示“无样本”，而非 0%。溢出、断网、阶段作废和取消不会混进该比例。

阶段按事件发生时归属：上个阶段收到的数据可能在下个阶段发送。重复包跨阶段时，原包可能已成功发送而余下副本被丢弃；因此不能将发送数与所有丢弃计数简单相加还原到达数。

## 如何解释体验差异

- 设置丢包 10%，实测配置丢弃 100 / 1000 = 10%，另有 200 个队列溢出：额外损失来源是过载，而不是把配置丢包率错误算成 30%。报告有溢出时会自动提示数量。
- UDP 样本少时，随机丢弃比例可能远离配置概率；没有 UDP 时这些参数不能验证。报告不会把 TCP 的可靠传输伪装成已测到 UDP 丢包。
- 设置 512 Kbps，平均只有 100 Kbps：可能无足够负载、服务器响应慢、延迟/背压/隧道开销；对照转发字节、连接数、限速等待、队列占用和各阶段持续时间。不能仅靠这些计数唯一证明某个外部原因。
- 短窗口高于配额：已经支付配额的数据遇到 socket 背压，缓冲可在解除阻塞时集中写出。报告保留真实窗口，不能把瞬时突发当作持续突破共享限速。
- 配置 500 ms 是单向代理附加等待；往返请求可能叠加上下行延迟，并受真实网络 RTT 影响。**本工具未测量 RTT、真实链路丢包或应用唯一有效吞吐。**
- **UDP-over-TCP** 隧道引入 TCP 重传、队头阻塞和背压，代理显式丢弃 UDP 不等于无线层丢包；正常阶段也有这些隧道特性。若需要真实无线网络语义，需要额外的网关/链路层测试手段。

## 存储与数据边界

Tauri 应用本地数据目录中：

- `weak-network-scenarios.json`：已保存场景，带 schemaVersion，按名称管理。
- `last-weak-network-report.json`：最近一次完成的报告，重启可读。只保留一份，下一次完成会替换；重要运行请逐次导出。

配置/报告采用同目录临时文件、写入同步后重命名。加载分别限制 1 MiB / 8 MiB；损坏配置报错且不会静默覆盖。报告含设备 ID、包名、时间、计数和配置；不采集 URL、包内容或代理口令，分享前仍应检查设备标识。未完成运行遇到进程崩溃时，不保证保留其实时采样，任务中心会标为中断。

## 验收清单

自动化入口：`npm run check`；额外严格检查：`cargo clippy --manifest-path src-tauri/Cargo.toml --all-targets -- -D warnings`。

自动测试覆盖配置往返、独立快照、校验上下限、四阶段时钟及晚切换、固定 seed、真实本地 TCP/UDP 转发计数、共享配额及改配额、断网后同一写入端恢复、UDP 半帧跨断网完整性、队列上限/释放、各种丢弃归因、连接跨阶段回收、Windows 原子覆盖及损坏/超限读取。

实机验收（自动测试不能替代）：

1. 更新助手 1.0.3，在目标应用中启动持续 TCP/UDP 负载；执行四阶段模板，观察高延迟、断网、恢复及阶段时间。
2. 保存、退出并重开桌面程序，载入同一配置再次执行；导出两份报告，核对 configured/seed 相同，runId 不同，测量数据独立。
3. 设置 UDP 丢包 100%，确认配置丢弃增长、转发为零、队列溢出为零；断网阶段应增长断网丢弃而非配置丢弃。
4. 设置 UDP 丢包 0%、高延迟/低带宽并施加持续突发负载，确认队列峰值不超过 256，出现溢出时独立提示。低负载不保证触发溢出。
5. 中途停止、任务中心取消、拔线、关闭桌面程序及结束后导出；核对结束原因、代理队列释放，以及任务中心记录的设备恢复结果。
6. 检查 JSON 不把配置延迟输出成实测 RTT，且包含 UDP-over-TCP、无样本、吞吐/队列口径等解释。

本次开发已进行本地自动化与 APK 构建验证；设备端真实应用的体验和断线恢复需要以上实机验收。


## 修改参数后重新应用的超时回归

2026-09-17 在 Redmi Note 8 Pro / Android 11 上复现：已有弱网运行时修改参数并再次应用，旧任务的 VPN 停止命令使用 `am start -W`。控制 Activity 发出停止请求后立即结束，等待界面启动完成的 ADB 命令超过桌面端 10 秒期限，但助手的状态标志已显示停止；后续发现这个标志不足以证明系统 VPN 已释放（见下节）。`-W` 的含义见 [Android ADB 文档](https://developer.android.com/tools/adb#am)。

桌面端现改用不带 `-W` 的命令派发，并单独查询 VPN 状态。停止请求报错后也会进行状态确认；确认最多等待 8 秒，状态不可读或仍在运行时不会宣称恢复成功。手动停止、旧任务替换和残留 VPN 清理使用同一确认流程。错误提示分别说明 VPN 与反向映射结果，并标明旧任务停止失败时新配置尚未启动。后续真实 VPN 释放修复需要助手 1.0.3，旧助手必须更新。

实机回归直接调用生产控制、状态查询、代理和清理函数，依次应用 80 / 200 / 500 ms 三组配置，每轮确认 VPN 启动后清理，再启动下一轮；清理耗时分别约 185 / 204 / 176 ms。这一轮仅确认了助手状态标志和反向映射，没有检查系统 VPN 网卡及服务绑定。后续发现助手标志存在误报，因此该结果不能作为真实网络恢复的通过证据；验收已按下节加强。

回归测试默认跳过，显式指定已授权且当前没有运行 VPN 的测试设备和包名后执行（会短暂启用所选应用的弱网，并在每轮结束清理）：

```powershell
$env:ADB_MONSTER_TEST_DEVICE = '测试设备序列号'
$env:ADB_MONSTER_TEST_PACKAGE = '测试应用包名'
cargo test --manifest-path src-tauri/Cargo.toml real_device_weak_network_reapply -- --ignored --nocapture
```

## 停止后 VPN 仍存在：1.0.3 修复与系统级验收

2026-09-17 在同一台 Redmi Note 8 Pro / Android 11 上确认：1.0.2 的状态广播为 `0|1|1.0.2||0`，但 `ip addr` 仍有本助手的 `10.111.222.1/30` 与 IPv6 VPN 地址，服务仍为前台服务，且存在来自 Android system 的 `android.net.VpnService` 绑定。原控制界面只调用 `stopService()` 并提前标记停止，实际资源清理只在 `onDestroy()`；系统绑定导致服务未销毁。

助手 1.0.3 使用显式服务停止动作，在手动停止、设备端到期、授权撤销和启动失败时主动停止原生隧道、关闭 TUN 文件描述符、移除前台通知，再停止服务。状态标志只在资源释放后更新。相关平台语义见 [绑定服务生命周期](https://developer.android.com/develop/background-work/services)与 [VPN 关闭接口](https://developer.android.com/reference/android/net/VpnService)。

桌面端现要求助手 1.0.3；停止确认额外检查本助手专用 VPN 地址是否已从系统网卡列表消失，不依赖固定名称 `tun0`，也不把其他 VPN 的网卡当成本助手。网卡查询失败时保留未确认状态。状态查询异常不会被静默替换成“未启用”。

实机回归使用上节命令，已在安装 1.0.3 后通过：

- 80 / 200 / 500 ms 三轮配置启动与手动停止，清理约 267 / 250 / 242 ms。
- 每轮独立检查真实 VPN 网卡消失、服务及系统绑定消失、专用 VPN 路由消失，以及反向映射移除。
- 每轮重复停止仍可成功，且不会重新建立 VPN。
- 单独给助手设置 10 秒有效期，在桌面不发送停止命令的情况下确认设备自行释放 VPN；随后清理测试用代理和反向映射。该 10 秒仅用于直接验证助手到期路径，不改变正式场景的总时长 +90 秒语义。

这次覆盖手机端真实 VPN 释放和恢复原有系统路由。目标应用业务连接的重建、其他 Android 版本以及完整桌面操作流程仍应按前述清单验收。
